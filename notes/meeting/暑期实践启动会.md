# Dobby 工程管理智能体 — 暑期实践启动会

---

## 一、主题实践

课题：**Dobby 工程管理智能体**。

这是一个面向建设工程质量安全的 AI 助手系统。我们的目标是让工程数据从"静态记录"变成"动态行动"——自动发现风险、生成任务、跟踪闭环、形成报告、工程管理服务。

我们团队一共 **11 位同学**，涵盖一年级到三年级，大家将围绕 Dobby 智能体的不同模块协同开发。

---

## 二、项目背景：为什么要做这个系统？

### 行业痛点

建设工程现场管理面临四大难题：

| 痛点 | 现状 | 后果 |
|------|------|------|
| **资料分散** | 日报、照片、整改单散在微信群、文件夹 | 信息孤岛，难以追溯 |
| **发现滞后** | 重大风险源靠人工巡检，被动发现 | 容易遗漏，事故隐患 |
| **闭环靠催** | 整改流程依赖人工通知、Excel 汇总 | 超期、遗漏、扯皮 |
| **经验难复用** | 项目结束后资料归档，经验流失 | 重复犯错，无法沉淀 |

### 我们的解决方案

> **Dobby：项目经理和安全总监的数字助手**

**核心理念：数据 → 行动**

```
数据汇聚 → 风险识别 → 任务生成 → 整改闭环 → 报告归档
   ↓           ↓           ↓           ↓           ↓
  多源采集    智能发现    自动派单    复核确认    知识沉淀
```

**不是再上一套重平台，而是让已有资料自动服务现场管理。**

## 三、系统定位：Dobby 能做什么？

### 五大智能体协作

```
┌─────────────────────────────────────────────────────────┐
│                  Dobby 工程管理智能体                      │
├─────────────────────────────────────────────────────────┤
│                                                          │
│  📊 数据汇聚智能体（前线资料员）                          │
│     → 收集整理纸质、影像、表单等原始资料                  │
│                                                          │
│  🧠 项目管理智能体（前线总指挥）                          │
│     → 统筹施工任务、进度、整改闭环                        │
│                                                          │
│  👁️ 隐患识别智能体（现场巡检观察员）                      │
│     → 识别隐患图片，固定违规证据                          │
│                                                          │
│  🗣️ 监管问答智能体（合规参谋）                           │
│     → 依托全库资料，应对督查、问询                        │
│                                                          │
│  💾 数据要素底座（后方物资总库）                          │
│     → 统一存放项目资料、隐患台账、过程数据                │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 核心场景：深基坑开挖前核查

以深基坑为例，展示完整闭环：

```
WBS 计划显示 3 号基坑即将开挖
    ↓
系统自动关联风险源台账（深基坑重大风险源）
    ↓
检查施工日报 → 发现防护尚未完成
    ↓
分析现场照片 → 识别临边防护缺失
    ↓
自动生成风险事件 + 整改任务（明确责任人、截止时间）
    ↓
施工单位上传整改照片和说明
    ↓
AI 初步复核 → 监理人工确认
    ↓
闭环归档 + 生成监管报告
```

## 四、技术架构：系统怎么实现？

### 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                    前端层 (Next.js)                        │
│   Dobby 对话 | 项目看板 | 任务管理 | 知识库 | 风险驾驶舱   │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│              API Gateway (FastAPI / Traefik)               │
└──────────────────────────────────────────────────────────┘
                          ↓
┌──────────────┬──────────────┬──────────────┬─────────────┐
│ Agent  │ Task Engine  │   WeKnora    │ MCP Servers │
│ Agent 运行时 │ 任务编排引擎  │  知识管理    │  业务工具   │
│              │              │              │             │
│ - 对话管理   │ LangGraph    │ RAG 问答     │ 隐患识别    │
│ - 多 Agent    │ + Celery     │ Wiki 生成    │ 监管问答    │
│ - 权限系统   │ + Redis      │ 文档解析     │ 数据分析    │
│ - 上下文管理 │ + PostgreSQL │ 混合检索     │ 通知推送    │
│ - 长记忆     │              │              │ 进度管理    │
└──────────────┴──────────────┴──────────────┴─────────────┘
                          ↓
┌──────────────────────────────────────────────────────────┐
│                    基础设施层                              │
│   PostgreSQL | Redis | MinIO | Neo4j(可选) | Langfuse    │
└──────────────────────────────────────────────────────────┘
```

### 关键技术模块

| 模块 | 说明 | 负责人 |
|------|------|--------|
| **数据+知识管理** | 数据底座、知识库建设、文档解析、数据治理 | 三年级 |
| **工程信息获取** | 从微信等渠道采集工程信息（日报、照片、整改单） | 二年级 |
| **任务管理** | 整改任务生成、派单、跟踪、闭环、超期提醒 | 二年级 |
| **上下文管理/角色/长记忆** | Agent 对话上下文、角色定义、长期记忆机制 | 二年级 |
| **MCP Server 开发** | 各类业务工具的标准接口（computer use、文档输出、数据分析等） | 一年级 |

- 任务状态跟踪（待处理→整改中→待复核→已闭环）

**关键产出：**
- 任务管理模块
- 任务状态机设计

---

#### 🧠 上下文管理/角色/长记忆（二年级 · 陈子楷、张骁桐）

**核心职责：**

**关键产出：**
- 上下文管理模块
- 角色系统
- 长记忆存储与检索
- Agent 协作协议

---

#### 🔧 MCP Server 开发（一年级 · 杨子杰、王子牧、张睿嘉、陈加恩、李姿苇）

> 为 Dobby 打造标准化的业务工具集

**核心职责：**
- 按照 MCP（Model Context Protocol）标准开发各类业务工具
- 每个同学负责 1 个 MCP Server
- 实现工具注册、调用、结果返回的完整链路

**MCP 功能：**

| 序号 | 负责 MCP Server | 
|------|----------------|
| **1** | Computer Use MCP | 
| **2** | 风险识别 MCP | 
| **3** | 数据分析 MCP | 
| **4** | 企业微信通知推送 MCP | 
| **5** | 文档生成 MCP | 

**每个 MCP Server 的标准结构：**

```
mcp-server-xxx/
├── server.py          # MCP Server 入口
├── tools/             # 工具定义
├── mcp-config.json    # 元数据声明
├── Dockerfile         # 容器化部署
├── requirements.txt   # 依赖
└── tests/             # 测试
```

**关键产出：**
- 5 个 MCP Server（可独立运行、可注册调用）
- MCP 开发规范文档
- 工具测试用例

- 上下文管理让 Agent 有记忆、有角色
- MCP Server 是 Agent 的"手和脚"，提供具体业务能力
