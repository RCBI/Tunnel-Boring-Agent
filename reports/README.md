# 周报归档

本目录用于统一归档项目成员的个人周报。周报采用 Amazon One Page 的思路：先写结论和事实，再写依据、风险和下一步，不使用工作流水账代替成果。

## 目录与命名

每周建立一个目录，每位同学提交一份 Markdown 文件：

```text
reports/
└── weekly/
    └── week-01/
        ├── TEMPLATE.md
        └── 姓名-模块名.md
```

例如：

```text
reports/weekly/week-01/张三-人员管理.md
```

## 提交规则

1. 从对应周次的 `TEMPLATE.md` 复制一份周报，不直接修改模板。
2. 周报文件名使用 `姓名-模块名.md`，模块名与分支负责范围保持一致。
3. 正文建议控制在 1000～1500 字，原则上打印后不超过一张 A4 纸。
4. 用户需求、数据库设计、静态原型等成果必须已经提交到同一分支，并在周报中使用仓库相对链接引用。
5. “已完成”必须有可检查的文件、页面、SQL、Commit 或其他证据。
6. 尚未确认的内容明确标为“假设”或“待确认”，不得写成已经确定的需求。
7. 学生将周报和成果提交到自己的功能分支，通过 Pull Request 请求合并到 `main`，不得直接向 `main` 推送。
8. Commit 信息统一使用：`docs(report): 姓名提交第XX周周报`。
9. PR 中应说明负责模块、主要产出、本地检查结果、风险及需要老师确认的事项。

## 成果文件建议位置

各模块可以在自己的模块文档目录中保存成果，例如：

```text
docs/modules/<module>/requirements.md
docs/modules/<module>/database.md
docs/modules/<module>/prototype/
```

如果模块已有约定目录，应优先沿用，避免重复创建文档。不要把大量图片或设计源文件直接塞进周报正文；周报只写摘要并提供链接。

## 验收重点

- 用户和使用场景是否明确；
- 核心需求是否有可验证的验收标准；
- 数据库结构是否能够支撑需求；
- 静态原型是否覆盖主要业务流程；
- 需求、数据库和原型是否相互一致；
- 风险、求助事项和下周计划是否具体、可执行。
